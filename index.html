Scope Basis and Assumptions

This plan delivers the complete ProEdits platform as specified in SRS v1.3, through to production deployment. All twelve SRS modules are built in full. There is no deferred phase, no reduced tier set and no partial add-on delivery.

What the platform does at go-live

The two non-negotiable rules

The SRS states only two requirements as firm rules rather than recommendations. Both constrain the architecture from the first week and are re-verified at every milestone gate.

FR-AI.6 · FR-UP.5 · Business Rule 6

Original files are never deleted

No delete route exists for an original. Deletion is blocked at the data-access layer and storage lifecycle rules exclude the originals prefix. An automated test asserts that project deletion, revision and add-on processing all leave originals intact. Built in Week 1, re-verified in Week 11.

“If an editor needs to manually fix windows, lighting, or other HDR problems, they may need access to the original exposures.”

FR-TRAFFIC.1 · Business Rule 4

One shared human queue

Exactly one service method creates an editing task. An architecture test fails the build if a task is created anywhere else. The method is idempotent, so no path can produce a duplicate task or silently drop one. Built in Week 4, before any consumer of it exists.

“Every AI failure or human request must enter your existing Traffic Management System.”

02

Delivery Model

Work is organised into module tracks. Each track corresponds to one functional area of the platform and runs across a defined set of weeks.

Every module track is resourced at 20 hours of effort in each week it is active.

A week in which five module tracks are active carries 100 hours; a week with six carries 120. Effort ramps up in Week 1 as the foundation is laid, holds at 100–120 hours through the build, and shifts entirely to testing and deployment in Weeks 11–12.

Feature freeze at Week 10

All feature development finishes at the end of Week 10. Weeks 11 and 12 contain no new functionality — only integration testing, cross-browser verification, performance measurement, a security pass, load testing, two defect rounds, staging soak, production build, go-live and handover.

A platform of this size cannot be tested meaningfully while it is still changing, and a deployment scheduled for the same week as the last feature is a deployment that slips.

Weekly working agreement

Per active track, per week: 16 h implementation, 3 h verification — tests written in the same week as the code they cover, never deferred — and 1 h coordination covering written status, cross-track integration points and open-issue chase.

Milestone gates

At the end of Weeks 4, 8 and 12: live demonstration against the exit-criteria checklist referenced to SRS identifiers; defect triage with blockers fixed inside the gate; the open-issue register updated; written sign-off before the next milestone begins.

Definition of Done — applies to every task without exception

Technology Stack

Exactly as confirmed. No substitutions.

PartTechnology

Three engines, one shared pipeline

The architecture the source flow document recommends and SRS §5.1 formalises. The three engines are separated in the codebase and in the deployment, not only conceptually, so that changing an AI model or vendor in one engine requires no change to the others, and so processing capacity grows independently of the web tier.

Engine 1

AI Pre-Processing

Python / OpenCV. Exposure detection, scene grouping, alignment, HDR merge, tone mapping, working-image render.

Engine 2

AI Add-On

Hosted AI APIs behind one internal adapter. Object removal, decluttering, lawn replacement, object manipulation, virtual staging.

Engine 3

Human Editing

NestJS workflow state in PostgreSQL with the staff interfaces. All human tiers, rejected AI results, and every revision.

All three feed one chain: Traffic Management → Editor Assignment → QA → Revision → Delivery.

Storage key convention

Fixed in Week 1 and used unchanged thereafter. Every saved result receives its own key; PostgreSQL records which original or earlier version it derives from. The bucket is private with no public access; every read is served through a time-limited presigned URL issued only after the API has authorised the request.

Dependency Order and Critical Path

The SRS sets out a technical dependency order for the build in §9.5. This plan follows it exactly, running tracks in parallel only where the dependency allows.

SeqItemWeeksWhy it sits here

Week 4 is the hinge of the programme

It closes the ingestion chain — upload, grouping, merge, working image — and simultaneously stands up the two shared services that everything in Milestone 2 consumes: the single queue entry point and the credit ledger. A slip in Week 4 propagates directly to every track in Weeks 5 through 9.

Most tracks run on the critical path. The items below carry float, listed in the order they should be used. Together they represent roughly 40 hours. Any use of them is agreed at a milestone gate and recorded, never taken silently.
